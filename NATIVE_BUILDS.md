# ZUNO Music — Native build and signing

## Targets

- Android: Capacitor 8, app id `com.zuno.music`, custom auth callback `zuno://auth/callback`.
- Desktop: Tauri 2, bundle identifier `com.zuno.music`, Windows / macOS / Linux. The `zuno://auth/callback` scheme is registered for desktop too, and the deep-link + single-instance plugins return email confirmations to the running app.

The Android Gradle project is generated by Capacitor during CI from the checked-in configuration. Tauri's desktop shell lives in `src-tauri/`.

## GitHub Actions outputs

Normal branch and pull-request runs create:
- A debug APK artifact. It is for testing only and is signed with the generated debug key.
- Desktop installer artifacts for Linux, Windows, and macOS.

A tag matching `v*` creates a signed Android release APK and a GitHub Release containing the Android APK and desktop installers.

## Required Android signing secrets

Create a private release keystore once, keep a secure backup, and add the following repository secrets under Settings → Secrets and variables → Actions:

| Secret | Value |
|---|---|
| `ZUNO_KEYSTORE_BASE64` | Base64-encoded `.jks` or `.keystore` file |
| `ZUNO_KEYSTORE_PASSWORD` | Keystore password |
| `ZUNO_KEY_ALIAS` | Key alias |
| `ZUNO_KEY_PASSWORD` | Key password |

Example Base64 encoding (run locally, do not commit the result):

```bash
base64 -w 0 zuno-release.jks
```

On Windows PowerShell:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("zuno-release.jks"))
```

The release job fails closed when any signing secret is missing. Never use a different signing key for updates: Android rejects an APK signed with a different certificate when it tries to update the installed app.

## Release

1. Add the four signing secrets once.
2. Push a semantic version tag, e.g. `git tag v0.1.0 && git push origin v0.1.0`.
3. The `ZUNO native app builds` workflow validates the frontend, builds Android and desktop packages, then publishes the files to GitHub Releases.
4. Download the APK from the GitHub Release or Android build artifact.

The app's update checker reads the latest published stable release. It reports an update only if the release tag is newer than the installed build version; when an APK asset exists it offers its direct download link.

## Important limitations

- A debug APK cannot update an installed release APK because the signing certificate differs.
- Android will still show its package-installer confirmation when a downloaded APK is installed. Android does not allow an ordinary app to silently replace itself outside managed/system update channels.
- Local imports and offline audio files remain on the device. Account sync currently covers library metadata/settings, not the audio binaries.
- iOS project generation and App Store signing are not included in this Android + desktop workflow.
